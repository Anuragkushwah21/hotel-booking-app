# Manual migration steps

This project has no `prisma/migrations/` history (the schema was being applied
with `prisma db push`). Apply these in order the first time you deploy the
dual-booking schema:

```bash
# 1. Repoint existing USER rows to GUEST (see 001_role_migration.sql)
psql "$DATABASE_URL" -f prisma/manual/001_role_migration.sql

# 2. Apply the new schema
pnpm prisma db push

# 3. Regenerate the client
pnpm prisma:generate
```

If you would rather start a proper migration history instead of `db push`:

```bash
pnpm prisma migrate dev --name dual_booking_baseline
```

...but run `001_role_migration.sql` first either way, otherwise the enum
change fails with `unsafe use of new value "GUEST" of enum type` or
`cannot drop value "USER" ... still in use`.

## 002_booking_reference.sql

Adds `Booking.reference` — the short booking number (`HB-7K4M2Q`) a guest
quotes at the desk or types into `/booking-status`. The value is generated by
`generate_booking_ref()` in the database, so seeds and manual inserts get one
without any application code.

```bash
psql "$DATABASE_URL" -f prisma/manual/002_booking_reference.sql
pnpm prisma:generate
```

Run it before `prisma db push`: the column's default calls the function, so the
function has to exist first. Existing rows are backfilled by the script.
